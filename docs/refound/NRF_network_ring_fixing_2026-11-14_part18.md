### 124. 2026-11-18: why a short run differs from the day run from its first epoch, and why GPS fails in the short key-off run of DOY 146 (a read)

**Why.** Stage R's key-off control `ptRc_n146` (DOY 146, 5 h) departs from today's `d24_n146` at the first epoch and its GPS is poor (section 121.3); the managing session found the same departure in the 2 h run `d24c32_n146` (exe nrf32), so the engine is not the cause, and section 102.1 had noted it without tracing. Asked: (1) what makes the first epoch depend on the run's length, confirmed by a run pair, and what a streamed network would do; (2) why GPS is poor in the short key-off run and normal in the short key-on run.

**Method** (exe `gnss_processor_cha_fp1.exe`; scripts in `_irdu_grades/scripts_s20/`, outputs in `_irdu_grades/reads_2026-11-18/`). The run-start output of `d24_n146` and `ptRc_n146` compared as sets of lines with the counts and the durations normalised; the first epoch's records compared; the code read (`src/core/network/driver/ApplicationNetworkSetup.cpp`, `src/core/network/solve/Sbasis.cpp` on `chain/audit` at 91f36cf). Runs: `rl24_n146` (`d24_n146`'s configuration, 24 h) and `rl5_n146` (`ptRc_n146`'s, 5 h), each stopped by this session after 45 epochs (`stop_after_epochs.ps1`, log `_irdu_grades/stop_after_epochs.log`; the engine has no epoch cap that keeps the full parse), and `rl2e_n146` (`ptRc_n146`'s configuration for 2 h with `processing.exact_epoch_time` true; exit 0, 240 epochs). **1. The first epoch depends on the configured length through the group-delay latch.**
- *The rule* (shown, code). With `network.sat_gf_datum` broadcast_tgd, the setup latches each satellite's broadcast group delay once per run for the geometry-free pin's right-hand side: the low median of the satellite's healthy navigation records (Galileo F/NAV preferred) whose clock epoch lies in the processing window [t0, t1) (`NetworkSbasis::latchBroadcastGroupDelays`, `Sbasis.cpp:121`; called at `ApplicationNetworkSetup.cpp:710`). The window ends at t0 + `max_duration_s`, or one second after the last synced epoch without a duration (`ApplicationNetworkSetup.cpp:357-361`). The same window feeds the broadcast health series (line 394), the broadcast clock a priori (line 607) and the product files named in the S contract (line 1707); in these configurations only the latch's line differs between the runs.
- *The difference* (shown). Of the run-start lines, as sets with counts normalised, `d24_n146` and `ptRc_n146` differ only in the latch's window and its result (and in the counts of synced epochs and removed observations): window [TOW 172800, 259200) against [172800, 190800); over 24 h, 22 Galileo satellites latch a value other than the file's first record (+0.0698 to +0.4886 m: E03, E06, E15, E30 +0.4886; E02, E04, E12, E13, E16 +0.4188; ...), over 5 h none does.
- *Its effect at the first epoch* (shown). The first epoch's Galileo code-bias records of the 5 h run minus the 24 h run equal minus the latch difference on the E1 codes (C1C, C1X) and minus 1.793 times it (f1²/f5²) on the E5a codes (C5Q, C5X): E04 −0.4188 and −0.7510 m, E03 −0.4886 and −0.8762 m, E31 −0.0698 and −0.1252 m; satellites whose latch did not change differ by at most 4 mm (E29 C1X 0.0039 m). The GPS records of the first epoch differ by at most 6.4 mm (no GPS latch changed).
- *The run pair* (shown). `rl24_n146` stopped at 45 epochs equals `d24_n146` over the first 20 epochs, data line for data line (10 357 lines); `rl5_n146` stopped at 45 epochs equals `ptRc_n146` over the same 20 epochs; the two differ from each other at the fourth data line (C E04 −0.2619 against −0.2555). What sets the first epoch is the configured length, not the number of epochs processed; and the key's exe reproduces exe nrf32's day run.
- *A streamed network* (code, no run). With `network.streaming.enable` the epochs come from the live front end (`ApplicationNetwork.cpp:322-345`), but the setup still forms the window from the configured files' synced epochs and `max_duration_s` before the stream starts, so the latch would follow whatever span those give. A network streamed without end has no window end: the rule as written cannot be causal there. The latch already has a causal fallback, the healthy record in force at the window start (used for a satellite with no record in the window). A day run, by contrast, latches with records up to 24 h after its first epoch.

### 125. 2026-11-18: the saved state of the chain and the ring fix (card CHA step S7 (b); pre-registered)

**Why.** A run resumed from a snapshot starts the chain's tree memory and the whole ring fix empty (card CHA, part 2, P9; part 3, the list of step S7 (a)): every held link and its integers, the settled flags' waits, the untied satellites' moves, the vertices seen in earlier trees and the pinned lives of the tree edges; and the loader drops the root and merge rows whenever a snapshot is written. A restarted network (a reboot, a streamed service) therefore loses every held integer and fixes again from nothing. The author's word of 2026-11-18 moved the saved state up the order (card CHA, the order change of 14:15).

**The build** (default off, the precedent of card CRS2's hold capture and restore). Two keys:
- `network.state_snapshot_chain_capture`, the write side: the snapshot carries the memory below as records of their own, and the warm-resume fingerprint carries a token for each key that shapes that memory (the ring fix's keys, the chain's event rows, the pair families, the phase-family table), so a snapshot written under other settings cold-starts the memory.
- `network.resume_chain_restore`, the read side: a warm resume restores those records. A snapshot without them restores none, and a run-start line says so (the rows then run without memory, as today).

The memory (the list of card CHA S7 (a)):
- the chain: the vertices seen in earlier trees (satellite bands and receiver bands), the last election's tree roots, the root row's pinned receiver phase-bias targets, the pinned lives of the tree edges, the arcs' anchor ages and the emitter's anchor baseline;
- the ring fix: the links (held integers, streaks, decision stamps, roots, the monitor's and the near-null guard's state), the last tree times, the certified edges, the settled sets and their waits, the cascade links, the first epoch, the previous targets, the untied satellites' times, and the two hand-offs (the pending moves, the pending re-opens); not its run counters, which each leg reports for itself;
- the emitter's state that depends on held values: the step declaration's baselines and pending release marks, the unsettled steps' last flags, the continuity guard's runs, datums and holds;
- the broadcast group-delay latch (RF-0c): each satellite's latched value and the window it was latched over.

With the capture key, the loader keeps the root and merge rows when a snapshot is written (their memory travels with it). The ledger rows of both keys are UNVALIDATED. Unit cases: a round trip of every new record, and the fingerprint's tokens.

**The group-delay latch** (the manager's point 3, checked in the code). The snapshot carries no group delay and no window: the setup latches into `setup.sat_gf_target_m`, which no record writes, over the window [first epoch, first epoch + `processing.max_duration_s`) of the run (`ApplicationNetworkSetup.cpp`, the window and the latch). A resumed leg runs the setup again and latches over its own window. The O3 rule named beside it is a rule of the record's time (a broadcast record takes force at its clock epoch, `navAvailabilityGpsSeconds`): a resumed leg feeds the staged records by the same rule from its first epoch, so the rule itself needs nothing saved. The latch therefore belongs to the saved memory: with the restore key, a resumed leg takes the saved values in place of its own latch, and a run-start line names the saved window and the satellites restored. The identity test gives the uninterrupted run and the saving run one window: the uninterrupted run is the saving run (it writes the snapshot at 2 h and continues to 3 h), so its latch is the 3 h one, and the resumed leg restores that latch. If rule change 11 (card CHA part 3: a causal latch, so that a short run is a prefix of a long one) is approved and built before this step, the test also runs with it.
